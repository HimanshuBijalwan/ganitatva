# Ganitatva — Scaffold Plan

Implements **ADR-002** (in-app stack) and **ADR-003** (content is data) from `docs/01-ARCHITECTURE.md`.

> **The hard rule this whole document exists to protect:**
> **Adding a concept must never require writing Dart.** Every folder boundary below is drawn to make that
> mechanically true, not just conventionally true. If a future change makes it necessary to touch `lib/` to
> ship a new concept, that's an engine bug — see `content/schema/concept.schema.json`'s own description
> field, which already says this.

This is a **plan**, not code — no Dart is written here (this agent writes only to `docs/platform/` and
`.github/workflows/`). It is the brief for whichever agent scaffolds `lib/` (Phase 0, item 5: "Skeleton app —
Riverpod + go_router + Drift wired, one screen").

## 1. The ENGINE / CONTENT boundary

```
Ganitatva/
├── lib/                    ← ENGINE (Dart). Knows HOW to render/evaluate/score. Never knows WHAT a
│                              specific concept teaches.
├── content/                 ← CONTENT (YAML data). Knows WHAT each concept teaches. Contains zero Dart.
├── tool/                    ← build-time bridge: compiles content/ → an asset the engine loads at runtime.
├── assets/content/          ← generated output of tool/content_compiler — gitignored, rebuilt every time.
├── test/                    ← engine tests (widget/unit/golden)
├── integration_test/        ← cross-platform e2e smoke tests
└── android/ ios/ macos/ windows/ linux/   ← generated by `flutter create .`, not hand-authored
```

The boundary is enforced two ways, not just documented:
1. **Mechanically** — `content/schema/concept.schema.json` requires a `manipulate.widget` on every concept
   (already written). A concept YAML that doesn't name a widget the engine ships fails validation in CI
   (`.github/workflows/build.yml` → `content-validate` job) before it can merge.
2. **Structurally** — the engine's widget registry (`lib/widgets/registry.dart`, sketched below) is a
   closed `enum`-keyed map. Content *selects* a widget by string key + JSON config; it cannot introduce new
   Dart behavior. This is what "content composes, engine provides" means in practice.

## 3. Why the content compiler is its OWN package (`tool/content_compiler/`)

ADR-003 says content is "compiled at build time into a binary bundle." If the `yaml` parsing package were a
dependency of the **app**, the app could technically read raw YAML at runtime — the boundary would be a
convention, not a fact. Putting the compiler in its own `tool/` package with its own `pubspec.yaml` makes it
structurally impossible for `lib/` to import a YAML parser: `flutter pub deps` on the app package simply
never has `yaml` in the graph. The app only ever reads `assets/content/bundle.json` (or a binary format —
JSON is fine to start; a packed format is a Phase 2+ optimization, not a Phase 0 concern).

`tool/content_compiler` does double duty: it's also where local validation happens before a `flutter build`
even starts, so a bad concept file fails fast on the operator's machine, not just in CI. (The CI
`content-validate` job in `.github/workflows/build.yml` runs the same schema against the same files
independently, in Python — deliberately not by shelling out to this Dart tool, so content validation doesn't
require the Flutter SDK to be installed on the CI runner that gates every PR. Two implementations of the
same schema check is a small amount of duplication in exchange for a much faster, Flutter-independent gate.)

## 4. Pushback flagged inline: `golden_toolkit` → `alchemist`

ADR-002 names `golden_toolkit` for golden tests. As of this writing, `golden_toolkit` (eBay Motors) is
**discontinued/unmaintained**; `alchemist` (Betterment) is its actively maintained successor and is what the
pubspec below pins. This is a one-line, mechanical substitution — same purpose (golden tests on widgets),
same rationale in ADR-002 ("a math diagram that renders wrong is a silent content bug"). Flagged here and in
this agent's final report so whoever owns `docs/01-ARCHITECTURE.md` can amend ADR-002's text; not changing
it unilaterally since it's outside this agent's write scope.

## 5. Routing shape (go_router)

Deep-linkable, and the URL shape doubles as the thing the knowledge graph's "map UI" navigates to:

```
/                              → home / knowledge graph map
/concept/:conceptId            → concept_player/concept_screen.dart, layer=hook (default entry)
/concept/:conceptId/:layer     → deep link into a specific layer (hook|intuition|manipulate|formalize|practice|connect)
/practice/:conceptId           → practice_layer in isolation (for spaced-repetition review sessions)
/profile                       → progress summary
```

`conceptId` is exactly the schema's `id` field (`"arithmetic.fractions-as-parts"`) — no separate ID mapping
layer, so a concept's URL is derivable from its YAML file alone.

## 6. State shape (Riverpod) — sketch, not final provider list

- `contentRepositoryProvider` — singleton, loads `bundle.json` once at app start
- `conceptProvider(id)` — `Provider.family`, typed `Concept` lookup
- `graphProvider` — the compiled prerequisite DAG + path-engine
- `appDatabaseProvider` — Drift DB instance (one per app, platform-appropriate file location via
  `drift_flutter`)
- `conceptProgressProvider(id)` — `StreamProvider.family` over the Drift `concept_progress` table (reactive:
  UI updates the instant a practice attempt is scored)
- `nextConceptProvider` — derived from `graphProvider` + progress, feeds the map UI's "what's next"

No BuildContext-threading anywhere in `content/`, `graph/`, or `progress/` — pure Riverpod, testable without
pumping a widget tree, per ADR-002's stated reason for choosing Riverpod.


Deliberately **not** included yet (flagged so they're not silently forgotten, not because they're wrong):
- **`flutter_hooks` / `hooks_riverpod`** — ADR-002 doesn't call for hooks; adding them would be a second way
  to do the same thing Riverpod already does. Skip unless a real pain point shows up in Phase 1.
- **Analytics/crash-reporting SDK** — out of scope while there's no backend and no user accounts; revisit at
  Phase 7 (Scale & Release) once there's something to report to.
- **`json_schema` (Dart)** — belongs in `tool/content_compiler`'s own pubspec (local pre-build validation),
  not the app's. Not pinned here for the same reason `yaml` isn't (§3).

## 8. What this scaffold plan deliberately defers

- Exact Drift table columns for `fsrs_schedule` — Phase 2 (FSRS lands then); the table is reserved in the
  folder plan now so the migration path exists, but its schema isn't designed yet.
- The binary-vs-JSON question for the compiled content bundle — JSON is the Phase 0–2 choice (simplicity,
  debuggability); a packed binary format is a legitimate Phase 3+ optimization once bundle size at ~180
  concepts is a measured problem, not a guessed one.
- Melos/multi-package workspace — single Flutter app package is the right size through at least Phase 2. If
  the widget kit (`lib/widgets/`) ever needs to be published or reused outside this app, that's the trigger
  to extract it into its own package under a `packages/` directory — not before.
